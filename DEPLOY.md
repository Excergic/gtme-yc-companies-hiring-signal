# Deploying

Target: a Hostinger (or any Ubuntu/Debian) VPS, via Docker Compose. State lives
on the host filesystem, so it survives rebuilds, container removal and reboots.

## One-time setup

SSH into the VPS and run:

```bash
curl -fsSL https://raw.githubusercontent.com/Excergic/gtme-yc-companies-hiring-signal/main/scripts/vps_bootstrap.sh | sudo bash
```

Or clone first and inspect before running, which is the better habit:

```bash
sudo git clone https://github.com/Excergic/gtme-yc-companies-hiring-signal.git /opt/gtm-leadgen
cd /opt/gtm-leadgen
less scripts/vps_bootstrap.sh
sudo bash scripts/vps_bootstrap.sh
```

The script is idempotent. It installs Docker and the Compose plugin if missing,
clones or pulls to `/opt/gtm-leadgen`, creates `.env` from `.env.example` with a
**generated `APP_TOKEN`**, builds, starts, waits for health, then prints the
token. It never overwrites an existing `.env`.

## Then set the remaining variables

```bash
sudo nano /opt/gtm-leadgen/.env
cd /opt/gtm-leadgen && sudo docker compose up -d
```

| Variable | Notes |
|---|---|
| `APP_TOKEN` | generated by the bootstrap. Required for `POST /api/run`; without it that endpoint returns 503 rather than exposing an unauthenticated trigger that can spend credits. |
| `DEEPLINE_API_KEY` | copy from `~/.local/deepline/code-deepline-com/.env` on your Mac. Needed only for stages 3 and 5; stages 1, 2 and 4 run without it. |
| `SCHEDULE_CRON` | `0 9 * * 1` = Monday 09:00. Standard 5-field cron. |
| `TZ` | the zone the cron is evaluated in, e.g. `Asia/Kolkata`. |
| `ALLOW_SPEND` | `0` until the Deepline balance is funded. `1` lets the weekly run pay for the funding gate. |
| `DOMAIN`, `EMAIL` | only for the optional TLS profile. |

Keep `.env` at mode 600. It holds your Deepline key.

## Networking

By default the app binds **`127.0.0.1:8000` only** - not reachable from the
internet. That is deliberate: the dashboard and read endpoints have no auth, so
exposing them publishes your lead list to anyone with the URL.

Reach it over an SSH tunnel:

```bash
ssh -L 8000:127.0.0.1:8000 user@your-vps
# then open http://127.0.0.1:8000 locally
```

To publish it properly with HTTPS: point a DNS A record at the VPS, set `DOMAIN`
and `EMAIL` in `.env`, then

```bash
cd /opt/gtm-leadgen
sudo docker compose --profile tls up -d
sudo ufw allow 80,443/tcp   # if ufw is enabled
```

Caddy gets a Let's Encrypt certificate automatically. Note this still leaves the
dashboard and CSV endpoints world-readable - put Caddy basic auth in front, or
keep using the tunnel, if the lead data should stay private.

## Updating after a push

```bash
sudo bash /opt/gtm-leadgen/scripts/vps_update.sh
```

Pulls, rebuilds, restarts, re-checks health, and keeps the TLS profile on if it
was already running.

## Operating it

```bash
cd /opt/gtm-leadgen
sudo docker compose ps                  # state and health
sudo docker compose logs -f --tail 50   # live logs
curl -s localhost:8000/api/status       # counts, last run, credit balance
curl -s -X POST -H "X-API-Token: $TOKEN" localhost:8000/api/run   # run now
```

Data on the host: `/opt/gtm-leadgen/out/*.csv` are the three deliverables,
`/opt/gtm-leadgen/data/` holds the caches, ledger and run logs. Back up
`data/stage_cache.csv` - it is the funding evidence you paid credits for.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/` | dashboard: counts, ICP companies, CSV links |
| GET | `/health` | liveness, config echo, whether a run is in flight |
| GET | `/api/status` | last run summary, bucket counts, credit balance |
| GET | `/api/leads/{bucket}` | JSON rows; `?new_only=true` for this week's additions |
| GET | `/api/leads/{bucket}.csv` | CSV download |
| POST | `/api/run` | trigger a run; needs `X-API-Token`; `?allow_spend=true` to override |
| GET | `/api/logs`, `/api/logs/{name}` | run logs |

`{bucket}` is `icp`, `needs_review` or `non_icp`.

## Scheduling

The schedule is in-process APScheduler, so it runs as long as the container
does; `restart: unless-stopped` plus the Docker service being enabled means it
comes back after a reboot. `misfire_grace_time` is 3600s and `coalesce` is on,
so a restart within an hour of the scheduled time still runs the job once.

Set `DISABLE_SCHEDULER=1` to serve the API with no schedule, and drive it from
host cron instead if you prefer:

```
0 9 * * 1 cd /opt/gtm-leadgen && docker compose exec -T app python3 scripts/harvest_yc.py && ...
```

## What is verified

Verified in Docker on **both** `linux/arm64` and `linux/amd64`, from a build
context identical to this repo:

- image builds clean, 541 MB; node 20.20.2, Python 3.11.2, deepline 0.3.225
- `docker compose up -d --build` reaches `(healthy)` and serves host-mounted data
- first boot on empty state seeds `stage_cache.csv` and nothing else
- a full run via `POST /api/run` finishes in ~33 s, every stage exiting 0
- state survives restart: the next run flags 0 new ICP contacts, proving the
  ledger persisted
- all three CSV endpoints, the dashboard, and token auth (401 without, 200 with)
- no personal data in any image layer

Not verified: this exact VPS. The bootstrap script is syntax-checked but has not
been run against a live Hostinger host.

### A note on changing counts

Two runs ten minutes apart returned 19 and 17 ICP contacts. That is not
non-determinism: the Humaans "Founding US GTM Lead" posting was pulled from YC's
board between them. The pipeline reports the board as it is at fetch time, so a
filled or withdrawn role disappears from `icp.csv`. The ledger still remembers
the contact was queued, but nothing marks the role closed - worth knowing if you
are mid-outreach on a lead that vanishes.

## Railway (alternative, unused)

`railway.toml` is kept for the Railway path. It needs a volume mounted at
`/data`, because Railway container filesystems are ephemeral and the funding
cache would otherwise be wiped on every deploy.
